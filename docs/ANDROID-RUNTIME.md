# Android 运行环境推进记录

**当前结果更新：** ARM32 系统、APK 安装和未登录隐私页已实测；随后取得部分运行时代码并由 REA 读出扫码方法。最新结果见 [运行时发现](ANDROID-RUNTIME-FINDINGS.md)。下文保留早期诊断历史，先前取消的权限请求不是当前阻碍。


此记录区分「模拟器进程启动」与「Android 系统可用」，不把安装工具当作业务代码已恢复。

## 已完成

- 检查当前云机：x86_64、5 个逻辑 CPU，无 /dev/kvm；Docker 服务可连接，但不能据此假设有可用的 Android 内核或加速设备。
- APK 原生库为 arm64-v8a / armeabi-v7a，需要匹配 ARM 运行环境；未直接把它当作纯 x86 应用。
- 从 Google 官方仓库元数据选定稳定版 Emulator 37.2.12、Platform-Tools 37.0.1，以及 API 24 的 ARMv7/ARM64 系统镜像。
- 每个下载包在解压前核对官方元数据中的大小、SHA-1，未更改预期校验值或关闭 TLS。
- 将 SDK、AVD、测试用户目录全部放在 /workspace/research-tools/android-runtime 下；未覆盖用户系统目录或仓库源码。

## 实测结果

1. `emulator -accel-check` 返回 3，说明当前主机的 KVM 加速条件不成立。
2. 当前主启动器拒绝 ARMv7 和 ARM64 AVD，相关错误已保留。切换 classic 参数也没有恢复旧引擎支持。
3. 同一官方发行包内的 ARM64 headless 后端报告支持 TCG。手动指定匹配的 ARM64 AVD后，后端进程实际启动，使用软件执行并建立本地管理服务。
4. 沙箱拒绝 ADB 的本机监听套接字；获得相应许可后，ADB 调试服务成功启动，但当时仅观察到模拟器 `offline`。
5. 没有取得 `sys.boot_completed=1` 或系统包请求的成功结果，因此不能声称 Android 系统已就绪；更不能声称已运行 APK 或得到解密后的业务类。

## 后续探测已准备但未获执行许可

工作区里已准备 `/workspace/research-tools/android-runtime/probe-runtime.py`：

- 只重启我们创建的隔离研究 AVD，记录内核启动日志；
- 使用明确的 emulator-5570 序列号，限制于该测试实例；
- 最长等待系统就绪 240 秒；进程存在、ADB offline 均不算成功；
- 只有系统已启动、系统包可检查时，才安装此前验签的原始官方 APK，观察未登录启动页；
- 不扫描真实二维码、不登录、不填写凭证、不创建订单、不支付；
- 最后停止本次探测进程，避免持续消耗 CPU。

该项需要在沙箱之外使用本机调试套接字；对应安装/启动测试权限请求被用户取消。实际没有产生探测结果文件或启动日志，之前的模拟器也仍是原进程，故未执行该安装/启动阶段。随后已停止此前持续占用 CPU 的自建模拟器。

取消的是该明确的权限请求，不是官方接口拒绝，也不是自动审批系统的策略拒绝。不能将取消当成同意，当前暂停在该运行时探测步骤。

事实摘要与工具/镜像校验元数据见 `evidence/runtime-readiness.json`。本次没有恢复加固后的扫码或蓝牙业务代码；现有 iPhone 快捷指令与已完成的源码适配不受影响。
